# UniTask, Task, Awaitable или корутины

Если вы задумывались, нужен ли вам `UniTask` и какие у него есть альтернативы, — эта заметка для вас. Разберёмся, какие инструменты есть для асинхронного кода в Unity, как они справляются с типичными игровыми задачами и какой из них удобнее.

Сразу уточню: это не туториал и не разбор синтаксиса. Это сравнение удобства и полезности. Местами субъективное, местами предвзятое. В общем — честное.

**Коротко:**

- **`Task`** — стандарт .NET, доступный сразу и без установки, но не ждите от него понимания Unity: ни про кадры, ни про игровое время он не знает.
- **`UniTask`** — если вы не против поставить в проект сторонний пакет, то берите без раздумий.
- **`Awaitable`** — если версия Unity 2023.1 или новее и вы готовы смириться с ограниченным функционалом.
- **Корутины** по-прежнему хороши и умеют всё необходимое для типичных игровых задач.

Дальше сравним их подробно, а в конце заметки соберём всё в сводную таблицу.

> Сравнение актуально для Unity 6. Unity активно развивает `Awaitable`, так что в новых версиях что-то могло измениться.
{: .aside}


## Участники

- **`Task`** — классическая асинхронность из .NET. Выступает в роли эталона.
- **`UniTask`** — альтернатива `Task`, сделанная специально для Unity. Это сторонний пакет и его нужно установить отдельно.
- **`Awaitable`** — встроенный в Unity инструмент, появился в версии 2023.1. Этакая альтернатива `UniTask` прямо из коробки.
- **Корутины** — старый, но надёжный способ писать последовательный асинхронный код в Unity.

Колбэки в сравнении не участвуют: `async/await` и так прячет их под удобным синтаксисом.


## Раунд 1: ожидание времени

Самый простой и популярный вид асинхронности — подождать немного и продолжить.

```csharp
// Task: только реальное время
await Task.Delay(1000);

// Awaitable: только игровое время, с учётом timeScale
await Awaitable.WaitForSecondsAsync(1f);

// UniTask: можно выбрать
await UniTask.Delay(1000);                         // с учётом timeScale
await UniTask.Delay(1000, ignoreTimeScale: true);  // без учёта timeScale

// Корутина: оба варианта
yield return new WaitForSeconds(1f);
yield return new WaitForSecondsRealtime(1f);
```

**`Task`** просто ждёт указанное время. Никакого `timeScale` и никакой связи с игровым циклом Unity — это обычный таймер .NET, который работает независимо от игры. А в WebGL `Task.Delay` и вовсе может зависнуть навсегда: таймеру нужны потоки, а WebGL их не поддерживает.

**`Awaitable`** позволяет задать только длительность. Таймер всегда учитывает `timeScale`, и выбора тут нет.

**`UniTask`** позволяет выбрать, учитывать `timeScale` или нет. А ещё можно указать фазу игрового цикла, в которой идёт отсчёт. Большинство этот параметр не трогает, но сама возможность делает `UniTask` самым гибким инструментом для задержек.

**Корутины** предлагают два проверенных временем варианта: `WaitForSeconds` и `WaitForSecondsRealtime`. Просто, понятно и ничего лишнего.

Почему выбор типа времени важен? Это хорошо видно на паузе. Обычно её делают через `Time.timeScale = 0`. Тогда таймер `Awaitable` в меню паузы просто замрёт: подсказка не исчезнет, анимация кнопки не доиграет. А `Task.Delay`, наоборот, паузы не заметит: перезарядка способности продолжит идти, пока игра стоит.

> Ещё одна особенность `Task.Delay`: он ничего не знает об игровом цикле и продолжит работу даже после выхода из Play Mode. Код после `await` выполнится, когда игра в редакторе уже остановлена.
{: .aside}

**Итог раунда:** `UniTask` даёт даже больше, чем обычно нужно. Рядом с ним — корутины. `Task` живёт в своём мире, не связанном с Unity, и ему это простительно. А вот `Awaitable` получает минус: родной инструмент Unity, а выбрать тип времени нельзя. Для меню паузы придётся писать свой таймер.


## Раунд 2: ожидание кадра

Здесь задача уже напрямую связана с игровым циклом: подождать один или несколько кадров и продолжить.

```csharp
// Task: кадров не знает

// Awaitable
await Awaitable.NextFrameAsync();
await Awaitable.EndOfFrameAsync();
await Awaitable.FixedUpdateAsync();

// UniTask
await UniTask.NextFrame();
await UniTask.DelayFrame(5);
await UniTask.WaitForEndOfFrame();
await UniTask.WaitForFixedUpdate();
await UniTask.Yield(PlayerLoopTiming.PreLateUpdate); // любая фаза игрового цикла

// Корутина
yield return null;
yield return new WaitForEndOfFrame();
yield return new WaitForFixedUpdate();
// несколько кадров — только циклом
```

**`Task`** не умеет «подождать кадр». Он вообще не знает, что такое кадры: это часть .NET, а не Unity. Научить его можно, например завершая `TaskCompletionSource` из `Update`. Но каждый `Task` — новый объект в куче. Если ждать кадр в каждом кадре, сборщику мусора всегда будет чем заняться, а в Unity это рано или поздно превращается в подёргивания.

**`Awaitable`** здесь чувствует себя уверенно: следующий кадр, конец кадра, следующий шаг физики. И экземпляры `Awaitable` берутся из пула, так что ждать кадр можно часто.

**`UniTask`** умеет всё то же самое и тоже почти без аллокаций. Плюс `DelayFrame`, чтобы пропустить сразу несколько кадров, и `Yield`, чтобы продолжить в любой фазе игрового цикла.

**Корутины** закрывают весь необходимый минимум. Для типичных игровых задач этого вполне хватает. Только `new WaitForEndOfFrame()` создаёт объект при каждом вызове, поэтому в частых корутинах его стоит создать один раз и переиспользовать.

> Небольшой секрет: начиная с Unity 2023.1, `UniTask.WaitForEndOfFrame()` под капотом вызывает `Awaitable.EndOfFrameAsync()`. Вот кто управляет всем из тени.
{: .aside}

**Итог раунда:** `Awaitable`, `UniTask` и корутины справляются одинаково хорошо, явного победителя среди них нет. `Task` выбывает: технически ждать кадр можно, но цена из-за аллокаций слишком высока.


## Раунд 3: ожидание события

Иногда нужно просто дождаться, пока что-то произойдёт: игрок нажал кнопку, загрузка закончилась, враг погиб.

**`Task`** предлагает `TaskCompletionSource<T>`. Подписались на событие, в обработчике вызвали `TrySetResult()`, отписались. Пишется один раз, дальше используется как шаблон.

Мелкая, но неприятная деталь: в Unity есть только обобщённый `TaskCompletionSource<T>`. Версия без параметра появилась в .NET 5, а Unity пока на него не перешла. Поэтому даже для события без результата приходится писать что-то вроде `TaskCompletionSource<bool>`.

**`Awaitable`** предлагает `AwaitableCompletionSource`, который работает по тому же принципу. Никаких сюрпризов.

**`UniTask`** предлагает сразу несколько вариантов:

- [UniTaskCompletionSource]({% link _unitask/010-UniTaskCompletionSource.md %}) — то же самое, что `TaskCompletionSource`;
- [AutoResetUniTaskCompletionSource]({% link _unitask/011-AutoResetUniTaskCompletionSource.md %}) — для разовых событий, берётся из пула и не создаёт лишних объектов;
- [свой IUniTaskSource]({% link _unitask/012-IUniTaskSource.md %}) — когда каждая аллокация на счету. Реализация сложнее, но полностью под контролем.

А для многих событий Unity в `UniTask` уже есть готовые методы, например `button.OnClickAsync()`.

**Корутины** устроены иначе. Нужно унаследоваться от `CustomYieldInstruction` и реализовать свойство `keepWaiting`:

```csharp
public sealed class WaitForClick : CustomYieldInstruction
{
    private bool _clicked;

    public WaitForClick(Button button)
    {
        // Отписка опущена, чтобы не перегружать пример
        button.onClick.AddListener(() => _clicked = true);
    }

    public override bool keepWaiting => !_clicked;
}
```

Корутина проверяет `keepWaiting` каждый кадр. Как только оно вернёт `false`, корутина продолжит выполнение. Механизм простой и понятный, но это опрос, а не реакция на событие: продолжение начнётся не в момент нажатия, а на следующей проверке. Для одного ожидания это незаметно. Но если таких ожиданий сотни, каждое из них каждый кадр спрашивает «ну что, уже?», даже когда ничего не происходит.

**Итог раунда:** все инструменты умеют ждать событие. У `Task` и `Awaitable` это работает одинаково и без сюрпризов. У `UniTask` больше вариантов и готовых решений, в том числе без лишних аллокаций. Корутины справляются, но по-своему: через опрос, а не через само событие.


## Раунд 4: несколько операций сразу

Иногда одной операции мало: нужно дождаться сразу нескольких или продолжить, как только завершится хотя бы одна.

```csharp
// Task
await Task.WhenAll(loadLevel, loadAudio);
await Task.WhenAny(timeout, playerInput);

// UniTask
await UniTask.WhenAll(loadLevel, loadAudio);
await UniTask.WhenAny(timeout, playerInput);

// Awaitable: готовых средств нет

// Корутина: «дождаться всех» только вручную
var level = StartCoroutine(LoadLevel());
var audio = StartCoroutine(LoadAudio());
yield return level;
yield return audio;
```

**`Task`** — эталон. `WhenAll` и `WhenAny` закрывают все типовые сценарии.

**`UniTask`** полностью повторяет возможности `Task`.

**`Awaitable`** не предлагает никаких средств для композиции. Сама документация Unity советует в таких случаях превращать `Awaitable` в `Task` своим методом-обёрткой. Работать будет, но тогда вернутся и аллокации `Task`.

**Корутины** — это, по сути, итераторы, которые выполняются шаг за шагом. «Дождаться всех» можно собрать вручную, как в примере выше. «Дождаться любую» — уже заметно сложнее.

На практике это важнее, чем кажется. Самый частый случай — таймаут: «ждём ответ сервера, но не дольше пяти секунд». С `WhenAny` это одна строка. Без него придётся писать свою обвязку и аккуратно отменять проигравшую операцию.

**Итог раунда:** явные лидеры — `Task` и `UniTask`. `Awaitable` на их фоне выглядит бедно, за что ему явный минус: даже простой таймаут придётся собирать вручную. К корутинам претензий нет: они долго и надёжно решали задачу последовательного выполнения, и отсутствие композиции им можно простить.


## Раунд 5: устойчивость к ошибкам использования

Последний раунд не про возможности, а про то, насколько легко сделать что-то не так.

**`Task`** прощает многое. Его можно сохранить в поле, передать в несколько мест и ждать сколько угодно раз: каждый получит один и тот же результат.

**Корутины** тоже устойчивы. Ждать корутину дважды обычно никому не нужно, а если что-то пошло не так, ошибка просто окажется в консоли.

**`UniTask` и `Awaitable`** ради отсутствия аллокаций берут внутренние объекты из пула. Отсюда главное правило: **каждую задачу нужно дождаться ровно один раз**. Сохранили задачу в поле и дождались из двух мест — у `UniTask` второй `await` закончится ошибкой. А про `Awaitable` в документации Unity прямо сказано, что ждать его дважды небезопасно.

> Справедливости ради, `UniTask` иногда всё-таки можно дождаться дважды. Но давайте договоримся, что нельзя. Сработает это или нет, зависит от того, как задача была создана внутри метода. Если что-то может сработать, а может и нет, то всегда считайте, что это не сработает.
{: .aside}

**Итог раунда:** `Task` и корутины надёжнее. `UniTask` и `Awaitable` быстрее и экономнее, но требуют аккуратности.


## А чем тогда отличаются корутины?

По раундам корутины почти везде справляются. Но есть два отличия, которые не про возможности, а про сам подход.

**Привязка к объекту.** Корутина привязана к `MonoBehaviour`, на котором запущена: объект уничтожили — корутина остановилась сама. `Task`, `Awaitable` и `UniTask` ни к чему не привязаны. Чтобы их ожидание прервалось вместе с объектом, нужно передать токен отмены. Это дело вкуса: привязка удобна, пока совпадает с вашими намерениями, а токен даёт полный контроль.

**Результат операции.** Корутина не умеет возвращать значение, поэтому результат передают через колбэк или поле:

```csharp
// Корутина: результат приходит в колбэк
StartCoroutine(LoadLevel(level => Show(level)));

// Task, UniTask, Awaitable: результат возвращается, как у обычного метода
var level = await LoadLevelAsync();
Show(level);
```

Пока операция одна, это терпимо. Но когда нужно загрузить уровень, по его данным загрузить врагов, а потом показать экран, колбэки начинают вкладываться друг в друга. Именно здесь от корутин чаще всего и уходят.


## Производительность

Если кратко — разницы нет, пока асинхронность используется по назначению, а не как замена игровому циклу при любой возможности.

Вот что значит «замена игровому циклу»:

```csharp
// Асинхронный цикл, который ждёт каждый кадр
async UniTaskVoid FollowTarget()
{
    while (true)
    {
        DoSomething();
        await UniTask.NextFrame();
    }
}
```

Можно сколько угодно мерить миллионы операций в секунду, но результат предсказуем: обычный `Update` всё равно быстрее. А когда вы ждёте события, загрузки или анимации, разницу между инструментами вы вряд ли почувствуете.

Пара слов об аллокациях. `UniTask` и `Awaitable` берут объекты из пула и почти не выделяют память, в отличие от `Task`. Но это скорее приятный бонус, чем причина выбрать библиотеку. Главное их преимущество в другом: они работают внутри Unity и прекрасно знают про игровой цикл, время и кадры. А память всё равно можно занять, например создавая `CancellationTokenSource` на каждую задачу.


## Итог

| | `Task` | `UniTask` | `Awaitable` | Корутины |
|---|---|---|---|---|
| Время | реальное | любое | игровое | любое |
| Кадры | дорого | ✓ | ✓ | ✓ |
| События | ✓ | ✓ | ✓ | опрос |
| Несколько операций | ✓ | ✓ | ✗ | вручную |
| Повторный `await` | ✓ | ✗ | ✗ | — |
| Установка | встроен | пакет | 2023.1+ | встроены |

Что выбрать:

- **`UniTask`** — если нет ограничений на сторонние пакеты. По удобству это тот же `Task`, но построенный вокруг игрового цикла Unity. Цена — аккуратность: каждую задачу ждать ровно один раз.
- **`Awaitable`** — если нет желания тянуть сторонние пакеты, а версия Unity позволяет. Главное — помнить об ограничениях: нет аналогов `WhenAll` и `WhenAny`, нельзя ждать дважды.
- **Корутины** — для простых последовательностей, привязанных к объекту, где не нужен результат операции. Это по-прежнему хороший рабочий инструмент.
- **`Task`** — для кода, который не связан с Unity: общие библиотеки, работа с сетью, вычисления в другом потоке. Для игровой логики он слишком мало знает об игре.

> Эти заметки посвящены `UniTask`, поэтому дальше все примеры будут на нём. Если вы только начинаете, загляните в заметку про [async/await в Unity]({% link _unitask/001-async-await-basic.md %}).
{: .aside}
