# Как организовать последовательный сценарий в UniTask

В Unity часто встречаются сценарии, состоящие из последовательных этапов: показ и скрытие интерфейсов, проигрывание анимаций и эффектов, и т.д. 

Например, сценарий показа окна подсказки может состоять из нескольких этапов:

``` 
OpenWindow → ShowContent → HideContent → CloseWindow
```

Иногда между отдельными этапами нужно встроить внешнюю логику.<br>
Например, после показа сообщения дождаться действия пользователя:

```
OpenWindow → ShowContent → [действие пользователя] → HideContent → CloseWindow
```

Самый очевидный способ решить такую задачу - создать отдельные методы для каждого шага:

``` csharp
await workflow.OpenWindowAsync();
await workflow.ShowContentAsync();

await WaitForUser();

await workflow.HideContentAsync();
await workflow.CloseWindowAsync();
```

Так внешний код получает полный контроль над последовательностью выполнения и может встроиться в любой нужный момент.


## Проблема 

На первый взгляд решение выглядит удобным, однако теперь **внешний код начинает зависеть от внутренней структуры сценария и наоборот**.

Вызывающий код знает:
- какие этапы существуют;
- в каком порядке они выполняются;
- какие методы нужно вызывать для корректного прохождения сценария.

В результате **ответственность за выполнение сценария фактически переходит во внешний код**. Сам сценарий больше не управляет собственной последовательностью выполнения, а лишь предоставляет набор методов для отдельных шагов.

Более того, заранее невозможно определить, какое разбиение на этапы окажется достаточным. Со временем может потребоваться встроиться внутрь одного из существующих шагов:

```
... → ShowContent → ...

... → ShowContent_1 → [действие пользователя] → ShowContent_2 → ...
```
В этом случае придётся обновить все места использования сценария и встроить новые вызовы в правильное место последовательности.

Вместо одного вызова:

``` csharp
await workflow.ShowContentAsync();
```

внешний код теперь должен знать о новых этапах и вызывать их в правильном порядке:

``` csharp
await workflow.ShowContent_1_Async();
await workflow.ShowContent_2_Async();
```

И чем чаще сценарий используется в проекте, тем дороже становятся подобные изменения. Любое изменение внутренней последовательности начинает затрагивать код, который вообще не должен знать о деталях её реализации.


## Решение

Если внешнему коду нужно встроиться внутрь асинхронного сценария, не обязательно открывать наружу каждый шаг.<br>
Достаточно предоставить возможность **дождаться нужного этапа выполнения**.

``` csharp
await workflow.RunToAsync(WindowState.ContentShown);
await WaitForUser();
await workflow.RunToAsync(WindowState.WindowClosed);
```

Теперь внешний код просто указывает состояние, до которого должен выполниться сценарий. **API описывает не устройство сценария, а точки интеграции с ним.**

> Фактически мы заменили набор отдельных методов одним, которые принимает параметр, указывающий на этап, которого необходимо достичь.

Когда вызывается:
``` csharp 
await workflow.RunToAsync(WindowState.ContentShown);
```
сценарий сам выполняет все необходимые промежуточные действия и завершает задачу после достижения состояния `ContentShown`.

Даже если внутренняя последовательность изменится, код использования останется прежним. Теперь важны не конкретные шаги, а достижение целевого состояния.

```
OpenWindow → ShowContent [ContentShown]

OpenWindow → ... → ShowContent_1 → ShowContent_2 [ContentShown]
```

Пока сценарий продолжает достигать состояния `ContentShown`, внешний код не требует изменений.

## Реализация

Основная задача состоит в том, чтобы вернуть вызывающему коду `UniTask`, который завершится после достижения нужного состояния.

Для этого каждому этапу соответствует своя асинхронная операция и собственный `UniTaskCompletionSource`:

``` csharp
private Func<UniTask>[] _steps;
private UniTaskCompletionSource[] _stepCompletionSources;
```

Метод `RunToAsync` возвращает задачу, связанную с запрошенным состоянием, и при необходимости запускает выполнение сценария:

``` csharp
public UniTask RunToAsync(int targetState)
{
    _targetState = targetState;

    if (_targetState > _currentState)
        RunAsync().Forget();

    return _stepCompletionSources[_targetState].Task;
}
```

После запуска сценарий последовательно выполняет шаги один за другим. После завершения очередного шага завершается связанная с ним задача:

``` csharp
private async UniTaskVoid RunAsync()
{
    while (_currentStep < _targetStep)
    {
        await _steps[_currentStep + 1]();
        
        _currentStep++;
 
        _stepCompletionSources[_currentStep].TrySetResult();
    }
}
```
За счёт этого любой код может дождаться конкретного этапа выполнения сценария, не управляя его внутренней последовательностью.

> Это сильно упрощённая реализация. В реальном проекте могут потребоваться остановка текущего процесса, сброс состояния, поддержка нескольких одновременных ожиданий одного этапа и другие возможности.

<details markdown="1">
<summary>Дополнительные пояснения</summary>
Использование `AutoResetUniTaskCompletionSource` помогает построить более гибкую систему. На каждый вызов создаётся источник, возвращающий `UniTask`.<br>
Вместо одного массива `UniTaskCompletionSource` уже потребуется массив коллекций `AutoResetUniTaskCompletionSource`, чтобы хранить источник для каждого запроса. Это позволяет достаточно просто реализовать как остановку так и сброс всей системы.

</details>




## Итог
Возможность дождаться конкретного этапа выполнения позволяет отделить внутреннюю реализацию сценария от кода, который его использует.

Сценарий отвечает только за собственные действия, а внешний код работает только с состояниями, которые для него важны.

За счёт этого **сценарии становятся самостоятельными и переиспользуемыми**. Каждый сценарий отвечает только за собственную последовательность действий, а **взаимодействие между ними строится через ожидание состояний, а не через вызов отдельных шагов**.

Изменение внутренней последовательности не требует изменения кода использования до тех пор, пока сохраняются публичные состояния, доступные для ожидания.
