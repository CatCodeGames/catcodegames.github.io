# Последовательные сценарии в UniTask

В Unity часто встречаются сценарии из нескольких последовательных этапов: показать и скрыть интерфейс, проиграть анимацию или эффект и так далее.

Например, показ окна подсказки может состоять из таких этапов:

```
OpenWindow → ShowContent → HideContent → CloseWindow
```

Иногда между этапами нужно встроить внешнюю логику. Например, после показа сообщения дождаться действия игрока:

```
OpenWindow → ShowContent → [действие игрока] → HideContent → CloseWindow
```

Самое очевидное решение — сделать отдельный метод для каждого шага:

```csharp
await workflow.OpenWindowAsync();
await workflow.ShowContentAsync();

await WaitForUser();

await workflow.HideContentAsync();
await workflow.CloseWindowAsync();
```

Внешний код получает полный контроль над последовательностью и может встроиться в любой момент.


## Проблема

На первый взгляд это удобно. Но теперь **внешний код зависит от внутреннего устройства сценария**.

Вызывающий код знает:

- какие этапы существуют;
- в каком порядке они выполняются;
- какие методы нужно вызвать, чтобы сценарий прошёл правильно.

Получается, что **за порядок шагов отвечает уже внешний код**. Сам сценарий больше не управляет своей последовательностью, а просто предоставляет набор методов.

К тому же заранее не угадать, какого разбиения на этапы хватит. Со временем может понадобиться встроиться внутрь одного из шагов:

```
... → ShowContent → ...

... → ShowContent_1 → [действие игрока] → ShowContent_2 → ...
```

Тогда придётся обновить все места, где используется сценарий. Вместо одного вызова:

```csharp
await workflow.ShowContentAsync();
```

внешний код теперь должен знать о новых этапах и вызывать их в правильном порядке:

```csharp
await workflow.ShowContent_1_Async();
await workflow.ShowContent_2_Async();
```

Чем чаще сценарий используется, тем дороже такие изменения. Любая правка внутренней последовательности задевает код, которому вообще не нужно знать эти детали.

> Знакомая история: метод назывался `ShowContent`, а через полгода внутри у него три шага, два флага и комментарий «не трогать».
{: .aside}


## Решение

Если внешнему коду нужно встроиться в сценарий, не обязательно открывать наружу каждый шаг. Достаточно дать возможность **дождаться нужного этапа**:

```csharp
await workflow.RunToAsync(WindowState.ContentShown);
await WaitForUser();
await workflow.RunToAsync(WindowState.WindowClosed);
```

Внешний код просто говорит, до какого состояния должен дойти сценарий. Сценарий сам выполняет все промежуточные шаги и завершает задачу, когда дойдёт до нужного состояния.

**API описывает не устройство сценария, а точки, в которых к нему можно подключиться.** Набор отдельных методов заменён одним, который принимает этап, до которого нужно дойти.

Даже если внутренняя последовательность изменится, вызывающий код останется прежним:

```
OpenWindow → ShowContent [ContentShown]

OpenWindow → ... → ShowContent_1 → ShowContent_2 [ContentShown]
```

Пока сценарий доходит до состояния `ContentShown`, внешний код менять не нужно.


## Реализация

Задача — вернуть вызывающему коду `UniTask`, который завершится, когда сценарий дойдёт до нужного состояния.

Каждому состоянию соответствует шаг, после которого оно наступает:

```csharp
public enum WindowState
{
    WindowOpened,   // после OpenWindow
    ContentShown,   // после ShowContent
    ContentHidden,  // после HideContent
    WindowClosed    // после CloseWindow
}
```

У каждого шага есть своя асинхронная операция и свой `UniTaskCompletionSource`, который завершится, когда шаг будет выполнен. `UniTaskCompletionSource` запоминает результат, поэтому дождаться шага можно и после того, как он уже выполнен. И ждать один и тот же шаг могут сразу несколько частей программы.

```csharp
private Func<UniTask>[] _steps;
private UniTaskCompletionSource[] _stepCompleted;

private int _currentStep = -1; // последний выполненный шаг
private int _targetStep = -1;  // до какого шага нужно дойти
private bool _isRunning;
```

Шаги перечисляются в том же порядке, что и состояния в `WindowState`, а для каждого шага создаётся свой источник:

```csharp
public WindowWorkflow()
{
    _steps = new Func<UniTask>[]
    {
        OpenWindowAsync,
        ShowContentAsync,
        HideContentAsync,
        CloseWindowAsync
    };

    _stepCompleted = new UniTaskCompletionSource[_steps.Length];
    for (int i = 0; i < _steps.Length; i++)
        _stepCompleted[i] = new UniTaskCompletionSource();
}
```

Сами `OpenWindowAsync()` и остальные — обычные асинхронные методы сценария: анимации, эффекты, всё что угодно. Наружу они больше не торчат и могут быть `private`.

`RunToAsync` запоминает цель, при необходимости запускает сценарий и возвращает задачу нужного шага:

```csharp
public UniTask RunToAsync(WindowState state)
{
    int step = (int)state;

    // Цель только растёт: если уже просили дойти дальше, назад не откатываемся.
    if (step > _targetStep)
        _targetStep = step;

    // Сценарий запускается один раз. Если он уже идёт, он сам дойдёт до новой цели.
    if (!_isRunning)
        RunAsync().Forget();

    return _stepCompleted[step].Task;
}
```

`Forget()` запускает `RunAsync()` и не ждёт его завершения: сценарий работает сам по себе, а `RunToAsync` сразу возвращает задачу нужного шага. Если этот шаг уже выполнен, его `UniTaskCompletionSource` уже завершён, и `await` сразу продолжит выполнение.

Сценарий выполняет шаги по одному и после каждого завершает связанную с ним задачу:

```csharp
private async UniTaskVoid RunAsync()
{
    _isRunning = true;
    while (_currentStep < _targetStep)
    {
        await _steps[_currentStep + 1]();
        _currentStep++;

        _stepCompleted[_currentStep].TrySetResult();
    }   
}
```

Так любой код может дождаться конкретного этапа сценария, не управляя его последовательностью.

Зачем нужен флаг `_isRunning`? Без него каждый новый вызов `RunToAsync` запускал бы ещё один `RunAsync`, и два цикла выполняли бы одни и те же шаги одновременно.

> Это упрощённая реализация. Например, сценарий здесь одноразовый: `UniTaskCompletionSource` нельзя сбросить, поэтому чтобы пройти сценарий заново, понадобится создать новые источники. В реальном проекте могут понадобиться и остановка, и сброс, и другие возможности.
{: .aside}


## Итог

Возможность дождаться конкретного этапа отделяет внутреннее устройство сценария от кода, который его использует. **Взаимодействие строится через ожидание состояний, а не через вызов отдельных шагов.**

Внутреннюю последовательность можно менять, не трогая код использования, пока сохраняются публичные состояния, которые можно ждать.
