# Не прячьте UniTask внутри результата

Если метод запускает асинхронную операцию, это должно быть очевидно из его API. Иначе асинхронная часть поведения оказывается скрыта от вызывающего кода.

> Это не тот случай, когда код обязательно сломается. Мы просто уменьшаем количество неочевидных мест, которые потом приходится держать в голове.

### Проблема

``` csharp
var result = character.Move(target);
Debug.Log(result.Distance);
```

Получается, что `Move()` выглядит как обычный метод, который просто вернул данные. Хотя на самом деле он ещё и запустил асинхронную операцию.

``` csharp
public struct MoveResult
{
    public float Distance;
    public UniTask Completion;
}
```

Здесь легко получить нужные данные и забыть про ожидание `Completion`, или вовсе его не заметить. 


### Сделайте асинхронность явной

Пусть `UniTask` будет самим результатом операции:

``` csharp
UniTask task = character.Move(target, out var distance);
await task;
```

Теперь по одному вызову уже понятно, что `Move()` запускает задачу, которую нужно дождаться.  

А если ждать не нужно:

``` csharp
character.Move(target, out var distance).Forget();
```

### Почему это особенно важно для `UniTask`

`UniTask` использует пулы и повторно использует внутренние объекты. Они возвращаются в пул, когда `UniTask` дожидаются через `await` и получают его результат.
Если спрятать `UniTask` внутри результата, про него легко забыть и потерять преимущества работы без лишних аллокаций.

> Не обязательно запрещать каждое неправильное действие. Если правильный способ использования можно выразить самим API, незачем заставлять разработчика помнить это правило.
