# Не прячьте UniTask внутри результата

Если метод запускает асинхронную операцию, это должно быть видно по его сигнатуре. Иначе вызывающий код может и не заметить, что что-то ещё выполняется.

> Это не тот случай, когда код обязательно сломается. Мы просто уменьшаем количество неочевидных мест, которые потом приходится держать в голове.
{: .aside}


## Проблема

Допустим, метод `Move()` запускает перемещение персонажа и сразу возвращает расстояние до цели. Чтобы вернуть и то и другое, результат собран в структуру:

```csharp
public struct MoveResult
{
    public float Distance;
    public UniTask Completion;
}
```

Вызывающий код выглядит так:

```csharp
var result = character.Move(target);
Debug.Log(result.Distance);
```

`Move()` выглядит как обычный метод, который просто вернул данные. Хотя на самом деле он ещё и запустил асинхронную операцию.

Здесь легко взять нужные данные и забыть дождаться `Completion`. Или вообще его не заметить.

Есть и вторая ловушка. `UniTask` можно дождаться только один раз, а структура при передаче копируется. Если `MoveResult` передали в другой метод и там тоже дождались `Completion`, второй `await` той же задачи закончится ошибкой.


## Сделайте асинхронность явной

Пусть `UniTask` будет самим результатом метода, а данные возвращаются через `out`:

```csharp
UniTask task = character.Move(target, out var distance);
await task;
```

Теперь по одному вызову видно, что `Move()` запускает задачу, которую нужно дождаться.

А если ждать не нужно, это тоже видно явно:

```csharp
character.Move(target, out var distance).Forget();
```

Сам метод при этом не помечается `async`: у `async`-методов не может быть `out`-параметров, компилятор этого не позволит. Поэтому метод считает данные сразу, а задачу берёт от отдельного асинхронного метода:

```csharp
public UniTask Move(Vector3 target, out float distance)
{
    distance = Vector3.Distance(transform.position, target);
    return MoveAsync(target);
}

private async UniTask MoveAsync(Vector3 target)
{
    // само перемещение
}
```

> Если `out` не нравится, можно просто разделить метод на два: `GetDistance(target)` и `MoveAsync(target)`. Главное, чтобы `UniTask` не прятался рядом с данными.
{: .aside}


## Почему это особенно важно для UniTask

`UniTask` старается не выделять память. Многие его внутренние объекты берутся из пула и возвращаются туда, когда задачу дождались через `await` или явно отпустили через `.Forget()`.

Если `UniTask` спрятан внутри результата, про него легко забыть. Тогда объект не вернётся в пул, и пропадает главное преимущество `UniTask` — работа почти без аллокаций.

> Не обязательно запрещать каждое неправильное действие. Если правильный способ использования можно выразить самим API, незачем заставлять разработчика помнить это правило.
{: .aside}
